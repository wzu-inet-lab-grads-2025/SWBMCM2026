## 第四问，同初始排程、同扰动的比较

统一采用队友二（2）的优化路线，在 0 s 完整下发，5 s 发生扰动，通信恢复后才可下发改派指令。按新增告警的方位、距离、高度，故障车编号和恢复时刻逐项匹配。本支原面板 126 项中有 125 项与队友主面板重叠，另 1 项为无扰动对照。再用本支原有搜索配置处理队友主面板全部 1,751 项，包括 72 个新增告警位置与七类扰动，未计入加密和灵敏度样本。

| 策略（全部以队友排程起步） | 全部告警开测的情景数 | 各情景完成率均值 | 最晚开测时间均值 | 最晚开测时间最大值 |
| --- | ---: | ---: | ---: | ---: |
| 严格保持，固定原车对、站位和任务 | 7 / 1,751 | 58.576% | 59.802 s | 60 s |
| 保持原任务，可用余车追加新告警（队友基线） | 583 / 1,751 | 83.248% | 48.084 s | 60 s |
| 重调度，原告警固定站位（队友逐情景择优） | 1,751 / 1,751 | 100% | 34.482 s | 57.990 s |
| 重调度，未开测原告警可换站（本支） | 1,751 / 1,751 | 100% | 25.292 s | 37.614 s |

两份回放器对严格保持策略的 1,751 组 `k/N` 与 `t_last` 全部吻合（时间容差 `1e-8 s`）。表中未全启时按题意记 60 s。队友主算例使用严格早于 60 s 的开测规则，本支包含端点，队友归档主情景中所有成功的末次开测均早于端点。各平均值以这份设计清单等权计算。

本支换站策略在 1,363 个情景更快，242 个持平，146 个更慢（时间容差 `1e-8 s`）。两支做法还在候选站集、路径和搜索方法上有差别。队友自己的换站灵敏度实验也能检验站位选择的作用。例如新增 `(90°, 50 m, 50 m)`、V2 故障、30 s 恢复时，队友固定旧站需 **57.990 s**，单独放开旧站后为 **36.373 s**，本支复算为 **34.663 s**。另有队友更快的情景，例如 `(60°, 50 m, 50 m)`、V5 故障、10 s 恢复时，两支分别为队友 **20.710 s**、本支 **22.800 s**。[逐情景底表](../experiments/b/snapshots/yyl_crosscheck/q4.csv)

只看两份原面板共有的 125 项，各自使用原初始排程时，本支与队友的最晚开测时间均值分别为 24.103 s、33.741 s。换成同一份队友排程后，均值分别为 24.598 s、33.741 s，双方仍全部按期启动。队友较强的“原任务保持、允许追加”基线值得与严格保持并列报告。对这 125 项，它使 41 项全部开测，严格保持只有 5 项全启。

## 复核范围与复跑

队友固定版本的 Q4 Git 归档验收在 Python 3.13 上复跑通过，覆盖 13,629 行策略评分、5,685 套已归档车队轨迹和 28,425 条逐车时间轴。该验收读取已求出的方案。本次跨分支实验另外直接用本支回放器运行保持和重调度策略，并用独立的事件审计器依据队友归档的名义时序核对两套回放。逐项检查 5 s 前已执行部分、故障退出、通信时段、视线、转向、同步开测和评分。[回放脚本](../experiments/b/crosscheck_yyl.py) · [事件审计规则](../experiments/b/q4_audit/README.md)
